# PushUp

PushUp is a four-player Steam **friend-slop** co-op climb built in Unity 6.5 URP. You and your friends try to push one ridiculous shared boulder up a giant mountain. The mountain is steep, the boulder is heavy, and the people helping you are absolutely capable of making everything worse on purpose.

Punch the boulder for a last-second save. Brace it before it rolls back into the valley. Grab a friend, shove them off a line, bait the attack dummy, or take a side path for a powerup while everyone else desperately tries to stop the run from collapsing. It is a game about teamwork right up until somebody decides trolling sounds funnier.

## The climb

- Get the boulder from base camp to the summit without losing it down the mountain.
- Use sprinting, crouch-sliding, jumping, grabbing, punching, and boulder push stance to make progress.
- Take risky side paths for temporary speed boosts, lighter-boulder assist, and a carryable anchor that pins the boulder in place.
- Knock friends down, get knocked down yourself, and recover with physical ragdoll-style reactions.
- Play alone offline or host a friends-only Steam lobby for up to four total players.

## Future bad ideas

The prototype is deliberately small, but the direction is big: stranger side paths, more mountain routes, nastier physics toys, ridiculous traversal powerups, higher-risk boulder modifiers, better character rigs and animations, richer summit outcomes, and more ways for a well-meaning friend to turn a near-perfect climb into a story everyone remembers. Voice chat, public matchmaking, persistence, achievements, host migration, polished art, and finished audio are future work rather than promises in the current build.

## Open and run

1. Open `C:\Repos\PushUp` in Unity Hub using Unity `6000.5.7f1`.
2. Open `Assets/PushUp/Scenes/Mountain.unity`.
3. Press Play, select **Play Offline Hill**, and use the displayed controls.
4. For a local two-client iteration, use **Host Local Development Game**, then **Start Hill**. FishNet uses Tugboat there; Steam playtest builds select the project-owned Steam sockets transport.

Private cross-platform Steam playtests use `PushUp.Editor.PushUpDevelopmentBuild.BuildSteamPlaytestAll`. This produces Windows x64 and Linux x64 development players with the `PUSHUP_STEAM_PLAYTEST` define so Steam Networking Sockets is selected even though the Development Build flag is enabled. These packages include App ID `480` strictly for friend testing and must never be uploaded as a release depot. Release identity is resolved at runtime from `-steamAppId`, `PUSHUP_STEAM_APP_ID`, Steam's environment, or an adjacent `steam_appid.txt`; a non-development build rejects an implicit Spacewar identity.

The scene, prefabs, materials, and spawn definitions can be generated by `PushUp.Editor.PushUpSceneBuilder.Build`. The generator replaces the prototype scene, so use it only when intentionally rebuilding the graybox rather than for ordinary level editing.

## Level design and spawning

- Open the `Level Authoring` hierarchy root. Player starts, world actors, powerups, and goals are organized into child groups.
- Add a marker with `GameObject > PushUp > World Spawn Point`, then choose a reusable definition from `Assets/PushUp/SpawnDefinitions` and place/rotate the marker.
- Use `GameObject > PushUp > Spawn Group` to organize conditional content. `Spawn At Run Start` controls initial activation; code may later call `RunDirector.ActivateGroup(groupId)` without duplicating existing spawns.
- Add player slots and summit goals through the corresponding `GameObject > PushUp` menus.
- Select `Level Authoring` and click **Validate Level Layout** before playtesting. Colored gizmos identify actors, the boulder, powerups, player slots, and the summit.
- `RunDirector` discovers the layout and spawn service automatically. Do not add prefab or Transform arrays to `RunDirector`; new content belongs in a `SpawnDefinition` and a scene marker.

## Prototype controls

- Move: WASD / left stick
- Sprint: left Shift / left stick press
- Crouch: left Ctrl / gamepad B
- Look: mouse / right stick
- Jump: Space / gamepad A
- Crouch-jump boost: press crouch shortly after jumping for extra upward and forward clearance
- Grab or terrain-brace: right mouse / gamepad X (hold)
- Boulder push stance: hold right mouse while aiming at the boulder; W pushes, Shift+W pushes harder, A/D repositions, and S or Jump exits
- Punch: left mouse / right trigger
- Use or release boulder anchor: Q / left bumper
- Menu: Escape / Start

## Multiplayer boundary

- `SessionFlowController` is the only menu-facing lifecycle owner. Offline, Steam, and local-development modes are mutually exclusive; Escape only opens Pause during a run and never starts a session.
- The retained uGUI flow separates lobby creation/joining, transport, authentication, replicated run readiness, and owned-player readiness. Every pending/failure state has Cancel, Leave, Retry, or Return.
- FishNet `4.7.2` provides GameObject lifecycle, ownership, client-authoritative player transforms, and RPC/state infrastructure. Local player physics runs at 60 Hz; player and boulder transforms are published at 30 Hz and player-arm poses at 20 Hz.
- Steamworks.NET `2025.164.1` provides Valve API bindings.
- `SteamSocketsTransport` is project code over `ISteamNetworkingSockets`; it carries FishNet messages through Steam Datagram Relay and accepts only Steam identities in the active lobby.
- Lobbies are friends-only and capped at host plus three friends. The host creates a waiting lobby, invites friends, and explicitly presses **Start Hill**. Waiting clients do not connect or spawn until the host starts; late joiners connect immediately after validating lobby/build/protocol identity. The in-game friend list remains available during a run even when Steam Overlay is unavailable. Departed players release their slot and can rejoin the same running lobby or accept a fresh direct invite.
- Player movement and physical knockdown are owner-authoritative, so normal network updates never correct the owning camera or Rigidbody. The shared boulder, actors, powerups, run state, and interaction validation remain host-authoritative. Validated hits are delivered exactly once to the victim owner; remote players are kinematic, interpolated replicas.
- Locomotion uses an explicit Rigidbody motor rather than raw force steering: separate acceleration/braking, slope projection, static-only step assistance, ground snap, tap-or-hold jump arcs, and dedicated walk/sprint boulder-push modes. Full boulder force is available only in the validated right-mouse push stance; ordinary collision provides only its natural physical nudge.

Read [Steam setup](Assets/PushUp/Documentation/SteamSetup.md) and [architecture](Assets/PushUp/Documentation/Architecture.md) before attempting a two-machine Steam test.

## Deliberate scaffold limits

The graybox implements the interaction-validation seam, owner-authoritative physical player roots, and jointed prototype arms needed for the first playable. Full latency simulation coverage, production character rigs/animation, voice chat, public matchmaking, persistence, achievements, host migration, and finished art/audio are intentionally out of scope.
